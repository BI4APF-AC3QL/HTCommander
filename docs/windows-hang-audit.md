# Windows 卡顿与队列停滞检查

检查日期：2026-10-02。对象为 `feature/remote-aprs-dashboard`，修复基于 `4baf64d`。重点场景为 Windows、N7500 蓝牙控制、APRS-IS 和手机远程地图。

本次发现并修复了可从代码和模拟测试验证的风险，但尚未复现用户电脑的整窗“未响应”，不能把以下问题全部认定为该故障的根因。本机崩溃日志仅有启动记录，没有异常调用栈。发送队列停滞与 Windows 主窗口卡死需要分别判断。

用户已确认故障表现为整个窗口不能操作，Windows 显示“未响应”。因此原生主线程等待和主 isolate 的计算突发为优先调查对象，不能把 TNC 队列停滞作为该症状的唯一解释。

## 问题与处理

| 问题 | 原有行为与影响 | 本次处理 |
|---|---|---|
| Windows 原生蓝牙断开在主线程关闭 socket | 控制和音频的 MethodChannel 断开处理直接调用 WinRT `socket.Close()`；驱动迟迟不返回时会阻塞 Windows 消息循环 | 在主线程标记连接不可用并移出连接表，实际关闭和资源释放交给持有连接所有权的后台线程；主线程不等待驱动关闭 |
| APRS-IS 输入缓冲无长度上限 | 每次收到数据都拼接并扫描全部未完成行；缺少换行时，内存和扫描开销持续增长 | 最大行长 512 字符，允许额外的行尾 CR；超过上限丢弃直到下一换行，继续处理后续合法行。只扫描新收到的块 |
| 地图全量快照随每个位置包发送 | 每个位置更新都复制整个站点索引，并同步触发 broker 的订阅与跨窗口传递 | 合并 500 ms 内的更新，每个窗口仅发布最新快照；ACK 和消息处理继续即时进行 |
| 蓝牙 TNC 分片永久等待回应 | 一旦发送回应丢失，in-flight 标志一直为真，后续分片不能发送；写入失败也没有处理 | 每个分片有 10 秒回应期限，写入失败/拒绝回应/超时均清空队列并断开连接，不自动重放 |
| TNC 队列未限制容量，忙时不能及时过期 | 持续提交数据可积累大量分片；频道一直忙时，过期包不能及时移除 | 最多 256 个排队分片；整包超过容量则拒绝并返回 0；每秒清理未开始的过期包。每包最多 64 个分片，符合六位分片编号 |
| Radio 连接监听与延迟初始化未释放 | 重新绑定 transport 时遗留旧订阅；对象 dispose 后仍可能处理传入数据；原有延迟初始化不能取消 | 重新绑定时取消旧订阅，dispose 后拒绝回调，初始化改用可取消 Timer；断开事件不再重复请求断开 |

电台分片回应没有可用于关联重试的独立事务编号。因此超时后必须终止该连接，避免迟到回应被当成下一包的回应。这个处理会造成一次可见断线，换取明确失败和可恢复状态。后续重连取决于现有连接管理策略；被清空的数据需要用户重新提交。已经交给电台的包可能继续完成，软件不能撤销已经发生的发射。

发送错误导致断开时，GAIA 接收解析器也会立即退出，避免使用旧读指针整理已经清空的缓冲区。GAIA 协议本身的载荷长度只有一个字节，正常解码后残留缓冲有协议上限；本次没有通过任意截断丢弃合法蓝牙数据。

## 验证

`src/test/hang_regression_test.dart` 包含八个无电台模拟测试：

1. 分 10,000 块输入共 1,000,000 字符，始终没有换行：保留缓冲不超过 513 字符，整条异常行只记录一次丢弃，遇到换行后能处理合法下一行，并保留正常长度边界。
2. 突发 1,000 个位置包：500 ms 内发布一次快照，保留最终位置；空闲时不继续重复广播。
3. 丢失 TNC 回应：10 秒后只断开一次，队列清空，迟到回应不会恢复发送。
4. 蓝牙写入失败：立即清空等待队列并断开。
5. 正常回应：依序推进分片，完成后取消超时处理。
6. 拒绝回应：接收解析过程中安全断开，不产生清空缓冲后的索引错误。
7. 忙频道：256 分片容量上限、整包拒绝、过期清理，且没有实际发送。
8. 更换连接与 dispose：旧 transport 不再触发回调，销毁后不执行延迟初始化。

全套 Flutter 测试：450 项通过。最后的 Dart 连接顺序调整后重跑相关测试，12 项通过；`flutter analyze` 无问题。Windows 原生插件已在本地 MSVC Release 目标重新编译并链接成功，存在工具链的 LNK4078 警告。此编译仅验证原生变更，分发包由当前分支 CI 构建，不把短路径缓存构建作为本次完整发行版。全部为模拟/本地测试，没有进行实际 RF 发射，也没有停止用户正在运行的应用或网关。

## 仍需实机定位的路径

- Windows 蓝牙驱动或 WinRT 调用：断开关闭操作已移到后台，原有连接、发现和读取等待也在后台；仍未取得实机挂起调用栈，不能证明该关闭操作就是用户这次故障的根因。此前检查未处理的退出路径，已在后续[原生接收与生命周期修复](windows-native-receive-hardening.md)中改为后台关闭和共享对象生命周期，并移除固定等待。该后续仍未证明实机故障根因。
- 远程音频慢客户端：浏览器播放缓冲已有上限；服务端 socket 输出没有明确的逐客户端字节预算，仍需要慢连接压力测试。
- APRS 历史数据库写入：采用异步 SQLite/WAL，但高流量情况下逐条提交的积压尚未做磁盘慢速压力测试。
- 设置与运行态混存：`RemoteClients` 位于 device 0，变化时会触发 SharedPreferences 保存；需要后续将运行态缓存与持久设置分离。
- 本地地图和音频解码的主 isolate：需要在真实窗口卡住时采样调用栈/CPU，判断是否存在持续计算或等待。

## 实机复测建议

使用包含本修复提交的新测试包，先仅进行接收测试。依次比较：只连接电台、开启 APRS-IS、打开地图、开启一个手机音频连接。每次只增加一项功能，记录出问题的时间和表现。

若再次出现：记录窗口是否能点击、Windows 是否显示“未响应”、CPU/内存是否持续升高，以及是否恰好发生蓝牙断线。运行日志中的 `TNC Bluetooth response timed out` 表示本次新增的队列超时保护已触发，不等同于窗口卡死。不要通过打开自动发射或信标来测试稳定性。
